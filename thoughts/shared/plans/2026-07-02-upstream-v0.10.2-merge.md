## Hard constraint

**No custom Gradient-DS functionality may be lost.** Every fork feature must work after the merge: cloud sync (OneDrive/Google Drive/Confluence/TOPdesk), typed KBs + subfolder tree + cloud KB layout, distributed doc pipeline (warren), skills + .skill bundles, TOTP 2FA + grace, password reset, invites, GDPR archival/retention/deletion, acceptance modal, feedback layers, agent proxy/picker/configs, generative UI (present_ui/context_usage/panel_filter/subagents), RAG filter, data warnings, docx/pdf export, feature flags, Weaviate adapter (+MT flag), HA Redis/socket fixes, branding.

## Overview

This is a v0.9.5 → v0.10.2 catch-up merge. Unlike the v0.9.5 merge (async cascade), the model/storage/socket/auth APIs are backward compatible this time. The two dominant work items are:

1. **Config subsystem rewrite (CRITICAL).** Upstream deleted `PersistentConfig`, `AppConfig`, and `app.state.config` entirely. Config is now per-key rows in the `config` table (migration `3ff2c63645b8`) accessed via async `Config.get / get_many / upsert` (`models/config.py`), with defaults registered in a `DEFAULT_CONFIG` dict + `Config.configure(...)`. Our fork has ~100 custom `PersistentConfig` entries and **~200+ read/write sites**, of which **~111 live in non-conflicted fork-only files** (services 63, custom routers 48) that will break at runtime, not import time. This is this merge's async-cascade equivalent.
2. **KB folders collision.** Upstream added a `knowledge_directory` table + `directory_id` FK on `knowledge_file` (migration `3c9b0ca343fd`). Our fork implements KB subfolders via `relative_path`/`source_item_id` columns on `knowledge_file` (migrations `b1d2e3f4a5c6` + `a1c2e3f4d5b6`) with a lazy tree (`/tree`, `/search` endpoints, `LazyKnowledgeTree` UI). Both designs coexist at the DB level (different columns). **During the merge** ours stays the working product UX and sync source of truth; **post-merge the decided direction (D2) is full adoption of upstream's directory model** via the fast-follow convergence in the backlog.

## Commit strategy

Stay in the merge (MERGE_HEAD persists across sessions). Resolve + `git add` file-by-file. **One merge commit** once all 148 files are resolved and the tree imports cleanly (end of Phase 5). Follow-up commits on the branch: fork-wide config caller migration (Phase 3 remainder if split out), migration-chain merge (Phase 6), fixes from verification (Phase 7). This mirrors the v0.9.5 precedent (merge commit → Phase-1.5-style follow-ups).

> **Session recovery:** if the merge state is ever lost: `cd .worktrees/feat/upstream-v0.10.2-merge && git reset --hard 10a8d1835 && git merge upstream/main` reproduces the exact same 148 conflicts.

## Execution model

Each phase is executed in a **dedicated implementation session** (kickoff per phase) using **subagent-driven development**: the orchestrating session runs on Fable and dispatches implementation subagents on **Opus** (`model: opus` per Agent call); the orchestrator reviews each subagent's diff against the phase recipe before `git add`. Dev environment: stack-1 (`tmux attach -t stack-1`) — `owui-be`/`owui-fe` windows crash-loop on conflict markers until Phases 2–5 land; restart them to re-test as resolution progresses. NOTE: `pyproject.toml`, `package-lock.json`, `uv.lock`, `backend/requirements*.txt` currently have their OURS side written to the working tree (env bootstrap only — index still unmerged; Phase 1d owns the real resolution). The OWUI venv uses a `.pth` + stub `open-webui` entry point instead of an editable install (the hatch hook can't build the conflicted frontend); after Phase 5, `pip install -e '.[soev]'` in the worktree venv restores the normal install.

Each phase is executed against the worktree paths only — never the main checkouts. Phases 1→7 are sequential on the merge branch (Phase 2 before 3 — the config contract must exist before callers migrate; Phase 4 before 5 — backend contracts before frontend). Phase 8 closes the branch. **Phase 9 is a parallel track in genai-utils** — it can start any time and does not block the merge PR. Each phase section above is written to be self-contained: scope, per-file recipes, and success criteria; the executing session should also read the relevant cluster analysis context in this plan's "Locked decisions" table before starting.

```python
import json, subprocess, sys
for f in files:  # the 60 conflicted translation.json paths
    ours = json.loads(subprocess.run(['git','show',f':2:{f}'.format(f=f)],capture_output=True,text=True).stdout)
```

## Phase 9 — Warren format parity (genai-utils, parallel track, ~3–5 days)

**Why:** decision (02-07-2026): **warren is the ONLY acceptable parse route** for sync/upload ingestion — no doc-processor fallback in the upload path. Target format set = the 27 tenant `allowed_extensions`: `pdf doc docx dotx xls xlsx xltx ppt pptx potx csv tsv txt text md markdown rtf odt ods odp html htm xml json epub msg rst`. Custom formats (ifc, …) explicitly out of scope. Verified baseline (02-07-2026 genai-utils inspection): 14/27 fully supported; `htm` parser-capable but not routed; 12 unsupported by warren.

Runs in **genai-utils** (`document_processing/distributed/pipeline/`) + one OWUI one-liner; does not block the merge PR, but MUST land before the sync-daemon cutover (daemon plan Phase 2+) since sync volume then flows exclusively through warren.

### 9a. Routing fix (OWUI, one-liner — may land as a follow-up commit on the merge branch)
Add `'htm'` to `PIPELINE_SUPPORTED_FORMATS` in `backend/open_webui/utils/doc_pipeline.py` (warren's `HtmlProcessor` already parses it).

### 9b. New warren parsers + allowlist entries (genai-utils), by difficulty tier
| Tier | Formats | Approach |
|---|---|---|
| Trivial | `tsv` (csv parser w/ tab dialect), `json`, `rst` (text-ish processors) | extend existing text/csv processors' `supported_types` |
| Moderate | `odt`, `ods`, `odp` (odfpy or OOXML conversion), `epub` (ebooklib), `msg` (extract-msg), `rtf` (striprtf/pandoc) | new processors in `processors/parsing/` |
| Hard — decide first | `doc`, `xls`, `ppt` (legacy binary; realistically LibreOffice-conversion sidecar) | **decision needed: build vs drop from the tenant list** — the legacy gradient-doc-processor's OOXML mapping for these was nominal-only anyway (python-docx can't read binary .doc) |

Each parser addition: processor + `supported_types` registration + bytes-sniffing entry where applicable + OWUI `PIPELINE_SUPPORTED_FORMATS` entry + fixture-based parse test.

### 9c. Deployment hardening (from the 02-07-2026 inspection)
- CI/image check: dp-worker image ships `warren[…http]==0.2.2` (`requirements.worker.txt`) — 0.2.1 lacks the `url` resolver and every presigned-GET fetch hard-fails (`UnknownLocationTypeError`).
- Presigned-GET TTL sized to survive RMQ backlog + warren retry ladder (expired presign = 403 = hard failure; only 404 retries). Review `PIPELINE_PRESIGN_TTL_SECONDS` default against observed queue latency.
